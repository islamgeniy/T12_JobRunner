# Протокол (Protocol) — черновик v0.3

Владелец: **Islam** · ветка `protocol-client` · файлы `src/protocol.h`, `src/protocol.c`, `src/client.c`

Этот документ — договор между тремя программами. Всё, что пересылается по сети, описано здесь. Чтобы изменить протокол, сначала меняем этот файл (через PR), потом код.

## 1. Общие правила

| Правило | Значение |
|---------|----------|
| Транспорт | TCP. Client → server и worker → server: подключается всегда тот, кто «снаружи», а server только слушает (`./server <port>`). |
| Сообщение | **Одна строка текста, заканчивается `\n`.** Слова разделены **одним пробелом**. |
| Чтение | Строку читаем **в цикле**, пока не встретим `\n`: один `write` не равен одному `read`, TCP может разрезать или склеить сообщения. |
| Длина строки | Максимум `MAX_LINE = 4096` байт вместе с `\n`. Более длинная строка — ошибка, соединение закрывается. |
| Команда задачи | Всегда **последнее поле**, занимает **весь остаток строки** (может содержать пробелы, кавычки, `\|`). Никто её не разбивает на слова. |
| Длина команды | Максимум `MAX_CMD = 3800` байт: чтобы строка журнала `SUBMIT T12-7 10 0 <cmd>` влезла в 4095 байт (лимит `journal_append`). |
| Символ `\n` в команде | Запрещён. `client` отказывается отправлять такую команду. |
| Бинарные данные | Только вывод задачи. Передаётся как **строка-заголовок с длиной** `<nbytes>\n`, за которой идут **ровно** `nbytes` сырых байт (length prefix). Конца строки после них нет. |
| Id задачи | `T<team>-<n>`, например `T12-7`. `n` начинается с 1 и никогда не повторяется. |
| SIGPIPE | Запись в сокет, который закрыла другая сторона, по умолчанию **убивает процесс** сигналом `SIGPIPE`. Все три программы в начале `main` вызывают `ignore_sigpipe()` (это `sigaction` с `SIG_IGN`), тогда `write` просто вернёт `-1`. |

### Состояния задачи (state)

Строка состояния — это **ровно тот текст**, который `client status` печатает после id:

| State | Значение | Финальное? |
|-------|----------|-----------|
| `QUEUED` | в очереди, ждёт свободный слот | нет |
| `RUNNING` | отдана worker | нет |
| `DONE <code>` | завершилась сама, `<code>` — exit code | да |
| `KILLED TIMEOUT` | убита worker по таймауту | да |
| `KILLED SIGNAL <n>` | убита сигналом `<n>` по другой причине (в том числе `SIGTERM` у worker → `KILLED SIGNAL 9`) | да |
| `CANCELLED` | отменена командой `cancel` | да |

## 2. Client ↔ Server

Один запрос, один ответ, затем client закрывает соединение.

### 2.1 Запросы (client → server)

| Запрос | Поля | Пример |
|--------|------|--------|
| `SUBMIT <timeout> <priority> <command>` | `timeout` ≥ 1 (секунды), `priority` 0–9 (по умолчанию 0) | `SUBMIT 10 0 sort big.txt` |
| `STATUS <id>` | | `STATUS T12-7` |
| `CANCEL <id>` | | `CANCEL T12-7` |
| `FETCH <id>` | | `FETCH T12-7` |

### 2.2 Ответы (server → client)

Ответ — одна строка: **первое слово — результат**, всё остальное — **текст, который client печатает как есть**.

| Первое слово | Client печатает остаток строки в | Exit code client |
|--------------|----------------------------------|------------------|
| `OK` | stdout | 0 |
| `NO` | stdout (для `FETCH` — stderr) | 1 |
| `UNKNOWN` | stdout | 2 |
| `ERR` | stderr | 4 |

Благодаря этому правилу client не знает ничего о состояниях задач: он печатает то, что прислал сервер.

| Запрос | Возможные ответы |
|--------|------------------|
| `SUBMIT` | `OK T12-7` · `ERR bad timeout` · `ERR bad priority` · `ERR command too long` |
| `STATUS` | `OK T12-7 QUEUED` · `OK T12-7 RUNNING` · `OK T12-7 DONE 0` · `OK T12-7 KILLED TIMEOUT` · `OK T12-7 KILLED SIGNAL 9` · `OK T12-7 CANCELLED` · `UNKNOWN T12-7 UNKNOWN` |
| `CANCEL` | `OK T12-7 CANCELLED` · `NO T12-7 ALREADY FINISHED` · `UNKNOWN T12-7 UNKNOWN` |
| `FETCH` | `OK <nbytes>` + ровно `nbytes` байт вывода · `NO T12-7 NOT FINISHED` · `UNKNOWN T12-7 UNKNOWN` |
| что-то непонятное | `ERR bad request` |

Ответ на `FETCH` с `OK`: client пишет в stdout **только** `nbytes` байт вывода, ничего не добавляя (без `OK`, без лишнего `\n`).

### 2.3 Ошибки, которые обрабатывает сам client (до сети)

| Ситуация | Client печатает в stderr | Exit code |
|----------|--------------------------|-----------|
| не удалось подключиться | `client: cannot connect to <host>:<port>` | **3** (по контракту) |
| сервер закрыл соединение, не ответив | `client: no reply from server` | 3 |
| неправильные аргументы, `timeout` < 1, `priority` вне 0–9, `\n` в команде | `usage: ...` | 4 |

## 3. Worker ↔ Server

Соединение долгое: worker подключается один раз и держит его, пока не завершится.

| Направление | Сообщение | Когда | Пример |
|-------------|-----------|-------|--------|
| W → S | `HELLO <K>` | первое сообщение после подключения | `HELLO 2` |
| S → W | `RUN <id> <timeout> <command>` | у worker есть свободный слот, политика выбрала задачу | `RUN T12-7 10 sort big.txt` |
| S → W | `CANCEL <id>` | client отменил задачу, которая `RUNNING` на этом worker | `CANCEL T12-7` |
| W → S | `REPORT <id> <nbytes> <state>` + `nbytes` байт вывода | задача завершилась (любым способом) | `REPORT T12-7 6 DONE 0` + `hello\n` |
| W → S | `BYE` | worker завершается по `SIGTERM` после всех `REPORT` | `BYE` |

Примечания:
- `<state>` в `REPORT` — финальное состояние из таблицы §1 (`DONE 3`, `KILLED TIMEOUT`, `KILLED SIGNAL 9`, `CANCELLED`), остаток строки. Server сохраняет его **как есть**.
- `nbytes` идёт **до** `state`, потому что `state` бывает из одного, двух или трёх слов.
- На `RUN` worker ничего не отвечает: server сам считает задачу `RUNNING` в момент отправки.
- Слотов у worker `K`. Server уменьшает счётчик свободных слотов при `RUN` и увеличивает при `REPORT`.
- Если worker пропал без `BYE` (соединение оборвалось), его задачи `RUNNING` обрабатывает компонент Durability (Abdulloh): по умолчанию они возвращаются в `QUEUED`.
- Максимальный размер вывода — `MAX_OUTPUT = 16 MiB`. Больший вывод worker обрезает, но **продолжает читать pipe до конца**, иначе задача зависнет на заполненном pipe.

### 3.1 Долгое соединение: отличие от `greet` из HW2

Основа та же, что в HW2 4.1 (`greet_client`/`greet_server`): одно соединение, много строк, чтение в цикле, пока `recv_line` не вернёт 0. Но у `greet` строгий порядок «вопрос → ответ», а здесь сообщения идут **в обе стороны в любой момент**: `RUN` и `CANCEL` от server, `REPORT` от worker. Отсюда два правила:

1. **На server в сокет одного worker пишут несколько потоков**: диспетчер шлёт `RUN`, поток клиента шлёт `CANCEL`. На сокете два `write` из разных потоков могут перемешаться (как большие записи в pipe, Slide 8). Поэтому у каждого worker-соединения свой **mutex на запись**: `lock` → `send_line` (или `send_line` + `send_all` для данных) → `unlock`. Читает из сокета только один поток.
2. **Worker читает сокет, пока его задачи выполняются.** При K > 1, или чтобы принять `CANCEL`, worker не может «застрять» в `waitpid` одной задачи. Как это сделать (поток на задачу, `poll` или SIGCHLD), решает владелец worker. Протокол требует одного: `REPORT` целиком (строка + байты вывода) пишется под тем же mutex на запись.

## 4. Сценарии (кто что шлёт)

### 4.1 Обычная задача

```
client                      server                          worker
  |-- SUBMIT 10 0 echo hello -->|                               |
  |<-------- OK T12-1 ----------|   (journal: SUBMIT)           |
  |                             |-- RUN T12-1 10 echo hello --->|
  |                             |   (journal: STATE RUNNING)    |  fork + exec
  |                             |<- REPORT T12-1 6 DONE 0 ------|
  |                             |<- "hello\n" (6 байт) ---------|
  |                             |   (out/T12-1 + journal: DONE) |
client2
  |-- STATUS T12-1 ------------>|
  |<-- OK T12-1 DONE 0 ---------|
client3
  |-- FETCH T12-1 ------------->|
  |<-- OK 6 ---------------------|
  |<-- "hello\n" ----------------|
```

### 4.2 Отмена задачи, которая выполняется

```
client                      server                          worker
  |-- CANCEL T12-5 ------------>|
  |                             |-- CANCEL T12-5 -------------->|  kill(-pgid, SIGKILL)
  |                             |<- REPORT T12-5 0 CANCELLED ---|  waitpid
  |<-- OK T12-5 CANCELLED ------|
```

Server отвечает client **только после** `REPORT` от worker. Иначе тест 5 (`pgrep` сразу после `cancel`) может найти ещё живой `sleep`.

Гонка: если задача успела завершиться сама, worker пришлёт `REPORT T12-5 ... DONE 0`, и server ответит client `NO T12-5 ALREADY FINISHED`.

Отмена задачи в `QUEUED`: server сразу меняет её состояние на `CANCELLED` и отвечает `OK T12-5 CANCELLED`, worker ничего не узнаёт.

## 5. Код: `src/protocol.h`

Общие функции для всех трёх программ. Никто не вызывает `read`/`write` на сокете напрямую.

```c
#define MAX_LINE   4096
#define MAX_CMD    3800
#define MAX_OUTPUT (16 * 1024 * 1024)

/* SIGPIPE → игнорировать (через sigaction): write в закрытый сокет вернёт -1. 0 / -1. */
int ignore_sigpipe(void);

/* Подключиться к host:port. fd или -1. В отличие от client_connect из net.h, НЕ завершает программу. */
int tcp_connect(const char *host, const char *port);

/* Пишет все n байт (цикл по write). 0 — успех, -1 — ошибка. */
int send_all(int fd, const void *data, size_t n);

/* Как printf, но в сокет, и сама добавляет '\n'. 0 / -1. */
int send_line(int fd, const char *fmt, ...);

/* Читает одну строку до '\n' ПО ОДНОМУ БАЙТУ (как read_line из net.h).
   1 — строка прочитана; 0 — соединение закрыто, полстроки выброшено;
   -1 — ошибка или строка не помещается в out. */
int recv_line(int fd, char *out, size_t size);

/* Читает ровно n байт. 0 / -1 (в том числе если соединение закрылось раньше). */
int recv_bytes(int fd, void *out, size_t n);

/* Строгий перевод текста в число из [min, max]. 0 / -1. */
int parse_long(const char *s, long min, long max, long *out);
```

Почему `recv_line` читает по одному байту: так она никогда не захватывает байты следующего сообщения. После заголовка `OK 6` следующие 6 байт вывода гарантированно лежат ещё в сокете, и `recv_bytes` читает их напрямую. Цена — один системный вызов на байт, но строки протокола короткие (десятки байт), а большой вывод `fetch` идёт через `recv_bytes` крупными кусками.

Начиная с v0.3, на одном сокете можно смешивать `recv_line`, `recv_bytes` и `read_line` из `net.h`: ни одна из них не читает больше, чем ей нужно.

## 6. Связь с курсом (Slide 10, `net.h`)

- **Framing.** Slide 10 называет два правила: «каждое сообщение заканчивается `\n`» и «каждое сообщение начинается со своей длины», и добавляет: «HTTP uses both: lines for the headers, a length for the body». Наш протокол устроен так же: строки для команд, длина для вывода задачи.
- **`server_listen` из `net.h` серверу подходит:** она включает `SO_REUSEADDR`, поэтому новый сервер на том же порту стартует сразу (тест 12).
- **`client_connect` из `net.h` клиенту не подходит:** при ошибке она печатает `connect: Connection refused` и делает `exit(1)` (проверено). Контракт требует `client: cannot connect to <host>:<port>` и код **3**. Поэтому есть `tcp_connect`.
- **`read_line` из `net.h` заменена на `recv_line`.** Проверено тестом, что `read_line` делает в двух случаях:
  - клиент оборвался посреди `SUBMIT 10 0 sle`: `read_line` возвращает 15, то есть **обрывок считается командой** (сервер создал бы задачу с обрезанной командой); `recv_line` возвращает 0, и задача не создаётся;
  - строка длиннее буфера: `read_line` **режет её на несколько сообщений**; `recv_line` возвращает -1, и соединение закрывается.

  Это ответ на вопрос из Details 1: «A client dies half way through a submit. Where does your read loop handle that?» — в ветке `got == 0` функции `recv_line`.

## 7. Открытые вопросы (решаем вместе до 29 ноября)

1. **Где хранится вывод задач.** Предлагаю: на server, в `out/<id>`. Тогда `FETCH` работает, даже если worker уже отключился, а Part 2 этого и требует (вывод записывается до того, как задача журналируется как завершённая).
2. **Как server обслуживает много клиентов.** Решает Amir. Важно для протокола: при `fork` на каждого клиента таблица задач у дочерних процессов **не общая**, поэтому проще **threads + mutex** на таблицу задач.
3. **Ждать ли подтверждения при `CANCEL`.** Предлагаю ждать `REPORT` (см. §4.2). Нужно, чтобы поток client на server умел ждать события от потока worker (например, через condition variable).
4. **Приоритет для FIFO.** Поле `priority` передаётся всегда. Политика, которой оно не нужно, его просто игнорирует.
5. **Завершение server по `SIGTERM`.** Решает Amir, но с учётом `net.h`: `server_accept` при любой ошибке `accept` завершает программу. Если обработчик SIGTERM поставлен без `SA_RESTART`, сервер выйдет с `accept: Interrupted system call`. Простой правильный путь (Slide 3, «safe work only: write, _exit, or set a flag»): в обработчике `write(1, "server: shutting down\n", 22)` и `_exit(0)`; listening socket ОС закроет сама.
